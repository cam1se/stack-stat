# 05 — Providers and local status store

The [core library manifest](../../crates/stack-stat-core/Cargo.toml) owns the `GitProvider`, `GitHubProvider`, and `StatusStoreProvider` contracts. Production adapters run external processes or read files, while tests inject fakes. Raw GraphQL wire types are normalized into provider records before composition; the [domain model](04-domain-and-config.md) has no CLI or GraphQL dependency.

The trait boundary makes branch switches, check transitions, and error paths testable with mutable in-memory fakes without live GitHub access. Fake executables on PATH would couple App behavior to CLI flag order and platform-specific scripts; a replay-only mode could not drive transitions or partial failures. The extra trait implementations are the deliberate cost of a stable, testable boundary.

## Git adapter

`CliGitProvider` discovers the checkout's top-level path and the Git common directory, which is shared by all worktrees. It reads HEAD via `git symbolic-ref --short HEAD`, branch refs via a single `git for-each-ref` invocation, and resolves explicit revisions with `git rev-parse --verify`. A detached checkout is represented by a distinct marker. Subprocess stdio is piped and optional Git locks are disabled for polling so the viewer does not interfere with concurrent agent work.

For an attached HEAD, the adapter finds the configured upstream and otherwise uses `origin/<branch>` when that remote-tracking ref exists. It compares that ref with the local branch through `git rev-list --left-right --count`, yielding in-sync, ahead, behind, or diverged state; no tracking ref is unpushed. A detached checkout remains in sync because no local branch is being compared.

## GitHub adapter

`CliGitHubProvider` resolves the repository owner and name once through `gh repo view`. Local Git supplies the checked-out branch; a `gh api graphql` lookup finds that branch's PR and reads `PullRequest.stack`. Two aliases in the same discovery request select the newest open PR and the newest PR across all lifecycle states; the open PR takes precedence, otherwise the latest lifecycle PR is used. This avoids stale selection when a branch name is reused. Each alias returns several candidates, and only a PR whose head repository owner matches the repository the branch pushes to is accepted, so a fork PR reusing the branch name is never taken for this checkout's PR. That owner comes from the branch's push remote in Git configuration (`branch.<name>.pushRemote`, `remote.pushDefault`, `branch.<name>.remote`, then `origin`) and falls back to the base repository owner when Git does not say; PRs whose head repository was deleted are skipped. The stack's base ref supplies trunk, entry positions supply layer order, and entry PRs supply identities, head refs, merged state, and merge-queue state. No local stack tracking or extension is needed. A branch without a PR, or a PR with a null stack, returns `NotInStack`; transport and parse failures remain errors rather than evidence of absence.

Discovery precedes the existing aliased `gh api graphql` detail/comparison query because its PR numbers and parent refs are query inputs. This adds one GraphQL round trip per ordinary in-stack poll, not one request per layer; stacks with more than 100 entries need additional discovery pages. For each non-merged layer, the detail query compares the remote parent ref—trunk for the first non-merged layer, otherwise the nearest non-merged layer below it—with the layer head; a positive `behindBy` requires a rebase. Missing or failed comparisons require no rebase. PR details include draft state, the latest reviews and outstanding review requests, and head-commit check runs plus legacy status contexts. A GraphQL response with partial repository data is parsed even if `gh api` exits nonzero because one alias failed; deleted or inaccessible PR aliases are omitted while valid siblings remain available. Local Git refs supply current local SHAs for check freshness; a remote layer need not have a local branch.

The remote rebase rule is recorded in [ADR-0001](../adr/0001-remote-rebase-status.md). [ADR-0002](../adr/0002-read-stack-from-github.md) records GitHub stack discovery, the base-chain counterexample, field mapping, and the read/action split.

Every `gh` process runs with piped input/output and prompts disabled. Read operations time out after 20 seconds; push and sync allow 120 seconds. The adapter classifies off-stack, rebase-conflict, rate-limit, authentication, network, and parse failures separately so the UI can retain the last useful snapshot or direct the user to an actionable fix. `gh stack sync` can exit 0 while printing `Sync aborted` when local and remote stacks diverge; the adapter reads both stdout and stderr and reports that as an abort, never as a successful sync. The adapter does not decide colors, sorting, or which checks the repository suppresses.

Checkout, push, and sync still use `gh stack`; only these actions check that the extension is installed. Missing extension errors direct the user to `gh extension install github/gh-stack` without blocking dashboard startup. Push and sync that lack local tracking return to a confirmation prompt; only approval runs `gh stack checkout <pr-number-or-branch>` to link the target and then retries the requested action. Declining does nothing beyond a cancellation status. Rebase conflicts do not trigger automatic linking or retries.

## Local check results

The file store lives at `<git-common-dir>/stack-stat/status/<encoded-branch>/<full-sha>.json`. Branch names are encoded as one platform-safe directory segment; `feat/api` does not create nested directories. The file contains a map of named results with outcome, optional message, and UTC timestamp. Cooperative readers take a shared lock and reporters/cleanup take an exclusive lock on a separate `status.lock` file. Writing merges a named result with its existing file and atomically replaces the file from a temporary sibling. This prevents a Windows reader's open handle from blocking replacement, while preserving complete JSON for readers across processes and worktrees. If no store exists, reads return empty without creating a lock file.

Malformed files are skipped with a warning while other entries remain visible. A new report may replace a malformed file. Cleanup retains each live branch's current-SHA entry and the most recently recorded older entry, deleting earlier entries and deleted branch directories. Retaining the older file is necessary to display a stale result after a commit or rebase. Both the file store and the in-memory fake use the same pure retention rule.

The Git common directory scopes reports to the clone and shares them among its worktrees. A user data directory would need a separate identity and cleanup policy across renamed and duplicate clones; tracked report files would turn transient, commit-specific evidence into source history.

## Adding provider behavior

Add a method to the narrow trait in [the providers module](../../crates/stack-stat-core/src/providers/mod.rs), implement the CLI/file adapter and fake with the same semantics, and add an observable contract test in the owning crate. Keep transport error classification at the adapter boundary; keep presentation decisions in the compositor.
